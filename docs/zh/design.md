# 设计文档

[English](../design.md)

本文描述一种**共享、有证据才写入的 Skill**：全团队的 agent 共用同一个 Skill，它随每次会话成长，并且只接受产生它的那次会话里有证据支撑的事实。

文中示例使用一个虚构的电商团队（`checkout`、`orders`、`wallet` 等服务）。这个模式与领域无关：运维、客服、数据分析、内部工具都适用。

<a id="0-background-from-a-local-skill-to-a-shared-one"></a>
## 0. 背景：从本地 Skill 到共享 Skill

最早的版本是 [agent-skill-patterns](https://github.com/tingfengyinyue/agent-skill-patterns)：一个基于文件的本地知识库，由一个人的 agent 读写。

**它是怎么工作的**

- **SPAR 循环**：每个任务都走"感知 → 规划 → 执行 → 反思"。*规划*阶段召回过去的教训；*反思*阶段回答四个固定问题（走弯路了吗？有更好的顺序吗？踩到坑了吗？下次该遵循什么规则？），并把答案写下来。
- **操作记忆（OM）**：每条教训是一个 Markdown 文件，包含触发条件（任务类型、服务、症状）、`better_action`（下次怎么做）、可信度（low → medium → high）、命中次数和生命周期（有效 → 被取代 / 废弃 / 晋升为 runbook）。
- **漏斗式加载**：先过滤一个很小的 JSON 索引，只读取命中的条目，必要时再读服务文档里的相关章节。一次加载通常只有一两百个 token。
- **双向链接与"时间桥梁"**：每条关系都存在两端。一条 OM 既指向产生它的历史事件，也通过触发条件指向以后应该用到它的任务。

它让一个人、以及拷贝过去的几个团队，排查明显变快了。但一到多人共享，局限就暴露出来：

| 本地版的问题 | 造成的后果 | 共享版怎么解决 |
|---|---|---|
| 每人一份拷贝 | 一个 agent 学到的东西永远到不了别人那里；各份拷贝越走越偏 | 服务端只有一份知识库，所有 agent 通过 MCP 读写 |
| agent 自己写教训、自己打可信度 | 错误的教训可以随意写进来，只能事后发现、手工订正（标"已被取代"、手动修改） | 写入要有本次会话的证据，没有证据的结论会被降级（§6） |
| 靠关键词索引召回 | 说法不同就召回不到；索引本身随笔记一起膨胀 | 标签 + 向量相似度 + 全文检索，综合排序（§5） |
| 链接、命中次数、生命周期全靠约定 | 需要有人持续维护一致，事后再用脚本重建关系 | 地图以图的形式存储，可以双向查询；可信度根据评价自动汇总 |
| 没有脱敏环节 | 凭证和内部标识混进笔记，没法直接分享 | 存储前做脱敏和注入检测（§10） |
| 没有使用记录 | 无法知道哪些教训真正有用 | 每次会话都记录召回、步骤、评价和修改 |
| 更新要改每一份拷贝 | 新规则只能传到重新拷贝过文件的人 | 本地只有一份很薄的引导文件；指令、笔记和地图实时获取（§9） |

**保留下来的做法**

- *反思*仍然是必经环节，产出仍然是带触发条件（标签）和一句"下次这样做"的经验笔记（`experience`）。
- *先便宜、后深入*：`skill_open` 只返回摘要，需要时才读全文。
- *时间桥梁*：一条经验仍然指向它的来源（现在是作为证据引用的会话步骤），也通过标签指向未来的任务。
- *生命周期*：用取代、冲突标记，以及带过期判断的最后验证时间（§5），代替人工维护的可信度和命中次数。

<a id="1-goals-and-non-goals"></a>
## 1. 目标与非目标

**目标**

- 全团队一份知识，而不是每人一份。
- 知识在正常使用中顺带变好，不需要专门有人"去更新文档"。
- 用户保留自己的凭证、运行自己的工具，服务端永远不需要访问生产系统。
- 共享知识保持可信：说得再笃定的 agent 也污染不了它。
- 尽量少的用户交互：从不问提问的人"要不要保存"。需要审核时，交给知识的负责人，而不是恰好在排查问题的人。

**非目标**

- 服务端不调用通用大模型。所有生成类工作（理解问题、制定计划、写结论和反思）都由用户的 agent 完成，服务端只做确定性处理和 embedding。
- 不做版本管理。每次修改都有记录，可以撤销。（目前也没有审批环节；规划中有按风险分级的审批队列，见 §6。）
- 不分发代码。agent 根据指令和笔记自己组织工具调用，Skill 不向用户电脑下发可执行脚本。

<a id="2-architecture"></a>
## 2. 架构

```
 用户电脑                                          Skill 服务端
┌──────────────────────────────┐   MCP / HTTP   ┌───────────────────────────────────┐
│ Agent（如 coding agent）       │ ─────────────▶ │ 会话服务                            │
│  + 引导文件（很薄）             │                │  - 解析问题、识别实体                │
│  + 用户自己的凭证               │ ◀───────────── │  - 检索笔记和地图                    │
│  + 本地工具 / CLI              │                │  - 记录步骤、结束会话                │
│                              │                │  - 校验并写入更新                    │
│ 所有查询都在本地执行             │                │  - 脱敏、注入检测                    │
└──────────────────────────────┘                ├───────────────────────────────────┤
                                                │ PostgreSQL + pgvector             │
                                                │  地图：节点、关系                    │
                                                │  笔记：条目（+ 向量）                │
                                                │  会话（步骤、修改记录）               │
                                                └───────────────────────────────────┘
```

同一个会话服务同时以 MCP 工具和 REST API 两种形式提供。MCP 是无状态的：每次调用都带 `session_id`，服务端可以多实例部署，不需要会话粘滞。

<a id="3-knowledge-model"></a>
## 3. 知识模型

四张表加一个物化视图。

### 地图

| 表 | 用途 |
|---|---|
| `graph_nodes` | 实体（`service:checkout`）和资源（`resource:prod:logstore:checkout-api`、`resource:prod:db:orders`）。每个节点有稳定的 `node_key`、所属领域 `domain`、用于识别的别名 `aliases`，以及自由格式的属性 `attributes`（索引字段、地域、代码仓库等）。 |
| `graph_edges` | 关系：调用 `calls`、拥有资源 `has_resource`、包含 `contains`（数据库包含表、父服务包含子服务）。关系的属性记录细节，例如共用日志库时需要的过滤条件。 |

地图回答的是"该去哪里查"。地图的任何修改都需要证据（见 §6）。

### 笔记

| 类型 | 示例 |
|---|---|
| `experience` 经验 | "checkout 超时：先查 wallet 服务的连接池，再查网关。"包含一句简短做法和完整正文。 |
| `document` 文档 | 指南中的一个章节，按标题切分。 |
| `case` 案例 | 保存下来的一次会话：问题摘要、结论、涉及的服务和资源。 |
| `instruction` 指令 | agent 必须遵循的规则，按条件加载（始终加载，或只在某个领域加载）。仅管理员可改。 |

每条笔记都有标签（服务、资源、任务类型、症状、错误码、关键词）；除指令外都有向量。

### 会话

`sessions` 表保存：问题、召回了什么、agent 记录的每一步、结论、对笔记的评价、反思，以及每次写入的修改记录 `changes`（含改前改后的快照）。

### 可信度

物化视图按笔记汇总：有多少不同的用户确认过它、多少人评为有用或有害。检索时用这个可信度乘以得分；已撤销的会话不计入。

<a id="4-session-lifecycle"></a>
## 4. 会话生命周期

| 工具 | 何时调用 | 作用 |
|---|---|---|
| `skill_open` | 收到问题 | 创建会话；返回指令、笔记、地图和引导文件版本 |
| `skill_search` / `skill_read` | agent 需要更多信息 | 返回更多笔记 / 一条笔记的全文 |
| `skill_log_step` | 每次操作之后 | 记录这一步：工具、资源、结果类别、简短摘要、发现的 ID |
| `skill_close` | 答案已就绪 | 保存结论；对从未出现在任何步骤里的 ID 发出警告 |
| `skill_get_session` | 反思时 | 返回压缩后的会话轨迹，通常由后台子 agent 读取 |
| `skill_update` | 会话结束后 | 写入评价、反思，以及有证据的知识 |

每一步的**结果类别**是证据门禁的基础：

| 类别 | 含义 | 是否算证据 |
|---|---|---|
| `ok` | 查到了数据 | 是 |
| `no_data` | 执行正常但没有匹配结果（并且自检确认数据源本身有数据） | 是 |
| `wrong_mapping` | 地图上的资源不对或不存在 | 是 |
| `no_permission` | 没有权限 | 否 |
| `env_mismatch` | 账号或环境不对 | 否 |
| `not_available`、`error` | 无法执行 | 否 |

<a id="5-retrieval"></a>
## 5. 检索

1. **解析**：用规则解析问题，按名称和别名识别实体，以及环境、时间窗、标识（trace ID、订单号）和错误码。
2. **召回**：标签匹配、向量相似度、全文检索三路并行召回笔记。
3. **打分**：`得分 = (0.45 · 标签 + 0.35 · 向量 + 0.20 · 全文) × 可信度 × 降权系数`。降权系数用于压低与问题无关领域的笔记，以及已过期的笔记（见下文）。
4. **地图**：从识别出的实体出发，展开到它们在所问环境下的资源和直接上下游。
5. **指令**按条件选取，不参与排序。

第一次只返回摘要，agent 需要时再读全文，保证首次响应小而快。

### 知识新鲜度

运行中系统的知识会悄悄过时：日志库改名、数据库迁移、接口变更。上周刚确认过的笔记和一年没人碰过的笔记，不应该被一视同仁。

- 每条笔记都有**最后验证日期**：它最近一次在有真实证据的会话中被确认有效的时间。导入的笔记从原始记录里的日期开始算，否则用最后更新时间。
- **90 天**没有被确认过的笔记，返回时带 `stale: true` 并降权（×0.8）。指令要求 agent 把它们当作线索，使用前先核实。
- 在有证据步骤的会话中被评为**有用**的笔记，会刷新最后验证日期；没有证据的会话里的评价不算数。
- 刷新只改验证日期，不改 `updated_at`，因此不会和别人正在进行的修改冲突。

这比完整的双时序建模刻意轻量（见[待讨论的问题](#12-open-questions)）：它回答的是"这条现在还能信吗"，而这正是 agent 真正需要知道的。

<a id="6-writing-knowledge-back"></a>
## 6. 知识写回

所有写入都通过一个调用 `skill_update` 完成：整体在一个事务里，每个操作一个 savepoint（一个操作失败不影响其他操作）。重复提交同一个 `update_id` 会直接返回第一次的结果。

### 证据门禁

规则是：**只有本次会话观察到了支撑它的东西，一个事实才能进入共享知识。**

| 操作 | 规则 |
|---|---|
| 一次证据步骤都没有的会话 | 只接受 `feedback`（评价）和 `reflection`（反思），其余一律返回 `needs_evidence` |
| `add_item`（新增笔记，或合并到已有笔记） | 必须引用证据步骤 |
| `save_case` | 必须引用证据步骤 |
| `update_item` | 有证据：覆盖（旧版本保留在 `changes` 中）。没有证据：新建一条并与旧笔记互相标记为**冲突**，两条连同各自的可信度都会展示给以后的 agent |
| 地图修改（`upsert_node`、`update_node`、`add_edge`、`invalidate_*`） | 必须引用证据步骤 |
| 指令 | 仅管理员 |

被引用的步骤必须存在于本次会话、必须是操作步骤，并且结果类别属于证据类。这由服务端校验，不能只凭 agent 的一句话。

### 其他写入规则

- **相似笔记**：新增笔记时，如果标题相同或向量相似度 ≥ 0.9，服务端返回 `needs_decision` 和候选列表。agent 带 `merge`（追加一节，从不删除）或 `new` 重新提交。
- **乐观锁**：修改时带上读取时的 `updated_at`，不一致返回 `stale`。
- **结论状态**：没有证据步骤的会话，结束时会把 `confirmed`（已确认）降为 `likely`（推断），`answered`（已回答）降为 `blocked`（受阻），并给出警告。
- **按会话撤销**：管理员可以根据 `changes` 记录，倒序撤销一次会话的全部写入。
- **目前是自动写入**：有证据就直接写入，不询问用户，事后管理员可以按会话撤销。这能让团队规模还小时知识持续增长，但不是审核问题的最终方案。

<a id="planned-risk-tiered-review-queue"></a>
### 规划：按风险分级的审批队列

证据门禁能拦住*没有*依据的写入，却判断不了有证据的写入*对不对*：agent 可能读了真实的日志，结论仍然是错的。写的人越来越多、有些笔记成了全团队依赖的基础以后，多一道人工确认就值得了，但只在出错代价大的地方。规划是按风险分流写入，而不是什么都审：

| 级别 | 例子 | 处理方式 |
|---|---|---|
| **自动** | 有证据的新经验和新案例；评价；反思；刷新最后验证日期；登记地图上还没有的仓库 | 立即生效，和现在一样 |
| **审批** | 覆盖高可信（确认次数多）的笔记；让笔记失效；删除或改变指向的地图修改（`invalidate_node`、`invalidate_edge`、修改资源标识）；与现有知识冲突的写入；撤销率高的贡献者的写入 | 作为**待审修改**保存，批准前不会召回给其他用户 |
| **仅管理员** | 指令（所有 agent 都要遵循的规则） | 由管理员修改，和现在一样 |

审批流程设想：

- **谁来审**：各领域的负责人（例如负责 `checkout` 的团队），永远不是提问的人。
- **看到什么**：改动前后的差异、引用的证据步骤及其摘要、会话的问题和结论、这条笔记的可信度历史。可以批准、驳回，或修改后批准，入口可以是网页或聊天卡片。
- **待审期间**：只有作者自己的会话能看到这条修改（标为待审），其他人仍然看到当前版本。互相冲突的待审修改放在一起审。
- **超时**：长时间没人审的待审修改会**过期**，而不是自动通过，避免队列悄悄变成后门。
- **调优**：按级别、按贡献者统计批准率和撤销率，反过来调整阈值。几乎总被批准的级别可以改为自动；经常被撤销的可以改为需要审批。
- **审计**：审批记录写进同一份 `changes` 日志，按会话撤销照样可用。

<a id="7-question-types"></a>
## 7. 问题分类

并不是每个问题都是排障。指令要求 agent 先分类：

| 类型 | 示例 | 流程 | 输出 |
|---|---|---|---|
| 排障 | "用户 123 下单失败，报 E4021" | 完整流程：规划 → 执行 → 记录 → 结论 → 反思 → 写回 | 报告：结论、根因、证据链、修复建议 |
| 数据查询 | "钱包 123 的余额是多少？" | 简短流程：1～2 次查询 → 回答 → 轻量反思 | 数值表格及数据来源 |
| 操作指引 | "怎么查钱包余额？" | 只读笔记，不执行任何操作 | 步骤和示例命令 |

分类规则和输出模板都写在一条指令里，修改时不需要重新部署任何东西。

<a id="8-repository-auto-registration"></a>
## 8. 代码仓库自动登记

团队的代码仓库很多，地图很少能全部收录。agent 开启会话时会上报当前目录的 git 远程地址。服务端把它规范化为 `group/name`（去掉主机、用户名和 token）后查找：

- **已登记**：返回这个仓库属于哪个实体，agent 从这里开始排查。
- **未登记**：提示 agent 分析这个仓库（README、包管理文件、部署配置），判断它的名称、领域和类型，然后提交 `register_repo`。

`register_repo` 以上报的远程地址作为证据，并有额外的保护：名称不能是通用词（`web`、`api` 等），也不能已被占用；把仓库挂到已有实体上时，名称必须对得上；只填补空白，从不覆盖已登记的仓库。

<a id="9-bootstrap-and-zero-touch-updates"></a>
## 9. 引导文件与零感知更新

本地只安装一份很小的引导文件：说明*什么时候*调用服务端、*怎么*跑完一次会话。其他一切（指令、笔记、地图）都在每次提问时实时获取。

这是共享 Skill 最实际的好处之一：**更新对用户无感知**。调整问题分类、收紧证据规则、加入过期提示，都只是修改了服务端的指令笔记；每位同事的下一次提问就用上了新规则，没有任何人需要重新安装或升级。对比本地版：一项改进只能传到记得重新拷贝文件的人那里。

`skill_open` 会返回当前引导文件的版本号。如果本地版本更旧，agent 会下载新版本并替换自己。

<a id="10-safety"></a>
## 10. 安全

- **服务端不存凭证**：用户在本地配置自己的只读凭证。
- **默认只读**：指令禁止在用户的系统上执行写操作；agent 只提出修改方案，由用户自己执行。
- **存储前脱敏**：从步骤和结论中去掉凭证和个人信息；写入共享笔记时还会去掉业务标识。
- **注入检测**：看起来像是对 agent 下指令的文本（"忽略之前的指令……"）不允许进入共享知识。笔记始终作为*数据*返回，与指令分开。
- **服务端日志不记录** Skill 接口的请求体和响应体。

<a id="lessons-learned"></a>
## 11. 踩过的坑

**agent 报告的是它打算做的，不是实际发生的。**
一个没有日志读取权限的 agent，把问题和一个旧案例对上，把结论标成"已确认"，最后还说"新发现已写入知识库"。它什么都没验证，也什么都没写入：最后那句话来自一个写死的输出模板。两项修复：服务端强制执行证据门禁，并降级没有验证的结论；模板必须如实报告写入调用的实际返回。

**"和历史案例一样"不是证据。**
历史案例是很好的线索，但不能当证据。如果允许它作为写入依据，一个错误的案例每被召回一次就会被强化一次。

**通用别名会污染识别。**
像 `scheduler`、`gateway` 这样的别名会命中不相关的问题。名称和别名必须具体，通用词一律拒绝。

**导入时要保留元数据。**
原来每个人的本地笔记里记录了事实何时成立、何时被观察到、哪条取代了哪条。第一次导入只保留了正文，丢掉了大部分这类信息，甚至把"部分被取代"当成了"失效"，悄悄隐藏了一条仍然有用的笔记。时间和来源字段是知识的一部分，不是装饰。

**要么只问一次，要么不问。**
早期版本每次写入都要用户确认。没人喜欢这样，大多数人直接点"是"。用证据校验替代人工确认之后，数据质量和使用体验都更好了。不过，向恰好在排查问题的人确认，和真正的审核不是一回事：出错代价大的修改，规划中的审批队列会交给负责这部分知识的人。

**不要把脚本放进 Skill。**
给每台电脑下发辅助脚本看起来很诱人，但脚本里固化的规则其实已经写在笔记里了，分发和校验代码反而增加了很多负担。笔记写得好，agent 自己就能组织好工具调用。

<a id="12-open-questions"></a>
## 12. 待讨论的问题

- **双时序历史**：被覆盖的事实是否要在记录时间之外，再保留一个有效时间窗口（何时成立 / 何时不再成立），像时序知识图谱那样，可以查询某个时间点当时认为的是什么？知识新鲜度（§5）已经覆盖了日常需要；等需要审计"做这个决定时我们知道什么"成为常态，完整历史才值得做。
- **身份认证**：每个用户一个个人令牌，让可信度和评价能正确归属。
- **数据保留**：原始问题和步骤保留多久，之后保留哪些。
- **效果评估**：衡量 Skill 是否真的在变好，例如同类问题的再次排查时间、召回命中率、被门禁拒绝的写入占比。
- **审批阈值**：什么算"高可信"、哪些地图修改需要审批、待审修改最多等多久就过期。
